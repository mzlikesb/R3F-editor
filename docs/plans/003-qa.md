## 반려 사유와 재현 방법

1. **진행 바가 남는 문제** (`src/ui/Panel.tsx:20-34`)
   - 원인: fill을 칠하는 곳은 rAF 루프 하나뿐이고, 루프는 `busy`(holding·pending·notice)일 때만 돈다. release·cancel·disconnect는 루프 밖에서 hold를 idle로 바꾼다. 그러면 `busy`가 false가 되고 루프가 멈추는데, fill은 0으로 다시 칠해지지 않는다. pending 중에 재연결 snapshot이 와서 idle이 될 때도 같다(100%로 남는다).
   - 재현: 고장 난 발전기 선택 → 수리 버튼을 0.5초 누르고 뗀다 → 라벨은 "꾹 눌러 수리 (1초)"로 돌아오는데 초록 바가 절반 채워진 채 멈춘다.
   - 고칠 방향: effect cleanup에서 `fill.current.style.transform = 'scaleX(0)'`로 되돌리거나, idle이 될 때 0으로 칠한다.
2. **잠긴 버튼에서 홀드가 시작되는 문제** (`src/ui/Panel.tsx:64-68`)
   - 원인: `onPointerDown`은 `fault`만 확인하고 `enabled`(`canRepair`)는 확인하지 않는다. `reduceHold`의 `press`도 확인하지 않는다. Chromium 계열은 disabled 버튼에도 pointer 이벤트를 보낸다. 그러면 재연결 중에 누를 때 홀드 → pending("수리 중…" 5초)이 돈다. 소켓은 OPEN인데 아직 snapshot을 받기 전인 짧은 틈에는 실제로 `repair`가 나간다.
   - 재현: Chrome에서 고장 상태로 연다 → 네트워크를 끊어 "재연결 중"으로 만든다 → 흐려진 수리 버튼을 1초 이상 누른다 → "계속 누르세요…"와 진행 바가 나오고, 그다음 "수리 중…"으로 바뀐다.
   - 고칠 방향: `onPointerDown` 맨 앞에 `if (!enabled) return;`을 둔다. 가능하면 `dispatchHold` 쪽에서도 `press`를 `canRepair`로 거른다.

## 이슈로 뺄 것

드물게만 생기는 문제다. 막지 않고 `bug` 이슈로 남긴다.

1. **서버 상태가 초기화되면 열린 탭이 모든 갱신을 버린다** (`src/sync.ts:39`, `:50`, `:54`, `:63`): 버전 비교만 하고 `instanceId`는 비교하지 않는다. DO 저장소가 리셋되면(로컬 `wrangler dev` 저장소 삭제, Preview DO 재생성) 버전이 낮아진다. 그러면 snapshot·fault·repaired를 새로고침할 때까지 모두 무시한다. 고칠 방향: `instanceId`가 다르면 snapshot을 무조건 받는다.
2. **유령 소켓이 presence와 첫 방문 판단을 흐린다** (`worker/BaseRoom.ts:45`, `:91`, `:113`): 소리 없이 끊긴 모바일 소켓은 런타임이 알아챌 때까지 `getWebSockets()`에 남는다. 그동안 접속자 수가 부풀고, 다음 방문자의 `connections === 1`이 실패한다. 이때는 자가 복구가 예약으로 대신 처리해서 20~40초 늦을 뿐 갇히지는 않는다. 고칠 방향: `getWebSocketAutoResponseTimestamp`가 오래된 소켓을 세기 전에 닫는다.
3. **연결 중 저장이 실패하면 반쯤 열린 소켓이 남는다** (`worker/BaseRoom.ts:42-59`): `acceptWebSocket`·snapshot·presence 다음에 `put`/`setAlarm`이 던지면 `fetch`가 거부된다. 클라는 101을 받지 못하는데 서버 소켓은 목록에 남는다. 고칠 방향: 결정·저장을 try/catch로 감싸 101은 돌려주고, 바로잡는 일은 자가 복구에 맡긴다.
4. **멀티터치로 홀드 중 선택이 풀리면 홀드가 끝까지 간다** (`src/App.tsx:19`, `src/ui/Panel.tsx:50`): 한 손가락으로 버튼을 누른 채 다른 손가락으로 빈 캔버스를 누르면 `select(null)`이 불린다. 그러면 버튼이 DOM에서 빠져 pointerup이 오지 않는다. Panel은 마운트된 채라 rAF tick이 계속 돌고, 1초 뒤 `repair`가 나간다. 고칠 방향: 선택이 풀리거나 버튼이 사라질 때 `cancel`을 보낸다.

## 제안

- `webSocketError`와 `webSocketClose`가 둘 다 `announcePresence`를 불러서, 끊김 한 번에 같은 presence가 두 번 나갈 수 있다(`worker/BaseRoom.ts:104`, `:108`). 동작에는 문제가 없다.
- GET이 아닌 `/api/base` 요청에 426 "Expected WebSocket upgrade"를 돌려준다(`worker/BaseRoom.ts:38`). 405가 더 맞다. 반대로 `/api/base`에 WS 업그레이드를 보내면 게임 소켓이 열린다. 경로로 나누는 편이 깔끔하다.
- 클라가 `PONG` 프레임도 `parseServerMessage`에 넘긴다(`src/net/socket.ts:63-66`). 파서가 null을 돌려주니 동작은 같다. 다만 tasks의 "PONG·PING 프레임은 parseServerMessage에 넘기지 않는다"와 어긋난다.
- 탭이 다시 보일 때(`visibilitychange` → visible) 바로 ping을 보내면, 백그라운드에서 죽은 연결을 최대 30초가 아니라 10초 안에 알아챈다.
