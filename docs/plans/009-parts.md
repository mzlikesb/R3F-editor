# 009 — 공용 부품 창고: 기다리는 동안 모으고, 모은 것으로 빨리 고친다

- 브랜치: `feat/009-parts`
- 등급: large
- 관련 이슈: Closes #101
- 마일스톤: M5 출시
- 상태: 플랜 리뷰

## Context

플레이테스트 세 번(PR #100, #104, #108)에서 페르소나 전원이 같은 말을 했다. 고장이 없는 시간(첫 접속 직후, 수리 직후)에 할 일이 없다. 재방문 의사는 "아니오" 또는 "모르겠다"였다(#101).

사용자 결정(#101, 2026-11-28): **공용 창고, 막지 않는 방식**.

- 고장이 없을 때 기지 주변에 부품 조각이 떨어진다. 누구든 탭하면 기지 공용 창고에 +1이 쌓인다.
- 수리할 때 창고에 부품이 있으면 1개를 쓰고 홀드가 짧아진다(1초 → 0.5초).
- 창고가 비어도 수리는 지금처럼 된다. 첫 방문 보장(경험 원칙 3)을 깨지 않는다.

이 기능은 `AGENTS.md`의 범위 줄("상호작용은 '수리' 1종")을 넓힌다. 범위 확장은 사용자 결정이다. 범위 줄은 별도 하네스 PR로 고친다.

새 상태는 **창고 수** 하나다(서버, 공용). 조각의 위치와 등장 시각은 시간에서 결정적으로 나오므로 상태가 아니다. 한 마일스톤에 상태 종류 2개까지라는 규칙 안이다. M5에서 이미 늘린 상태는 클라이언트 콤보 하나다.

경험 원칙:

- 1(다른 사람이 있다는 게 보인다): 남이 모은 부품으로 내가 빨리 고친다. 창고 수가 모두에게 같이 움직인다.
- 2(기지는 계속 살아 있다): 조각이 계속 떨어진다.
- 4(손맛): 줍는 탭에 작은 반응, 빠른 수리.

## 만들 것

### A. 서버 (DO)

1. **상태**: `BaseState`에 두 필드를 더한다.
   - `parts: number`: 창고 수, 0 이상 `PARTS_CAP`(5) 이하
   - `lastPartSlot: number`: 마지막으로 주운 조각의 칸 번호, 처음엔 -1
   - 저장 키는 `base:v2` 그대로다. 필드가 없는 저장본을 읽으면 `parts = 0`, `lastPartSlot = -1`로 채운다. 마이그레이션은 쓰기 없이 읽을 때 채우는 것뿐이다. **DO 저장 형식 변경이므로 이 플랜의 승인이 곧 그 승인이다**(`AGENTS.md` 멈춤 조건).
2. **조각 칸**: `slot = floor(now / PART_SLOT_MS)`(`PART_SLOT_MS` = 8초). 칸 하나에 조각 하나다. 위치는 `partPosition(slot)`(시드 해시, 기지 반경 안의 빈 땅, 모듈·탭 상자와 겹치지 않음)이 정한다. 위치 함수는 `shared/`에 두고 서버와 클라이언트가 같이 쓴다.
3. **줍기 메시지**: 클라이언트 → 서버 `collect { slot }`.
   - 받아들이는 조건: `slot`이 지금 칸이거나 바로 전 칸이다(경계 여유). `slot > lastPartSlot`이고, `parts < PARTS_CAP`이며, 고장이 0개다.
   - 받아들이면 `parts += 1`, `lastPartSlot = slot`, `version += 1`을 하고 저장한 뒤 모두에게 `parts { count, slot, mine }`을 보낸다. `mine`은 요청한 소켓에만 true다.
   - 조건이 안 맞으면 무시한다. 같은 칸을 두 번 주울 수 없다(멱등).
4. **수리에서 쓰기**: `repair { faultId }`가 받아들여질 때 `parts > 0`이면 `parts -= 1`을 하고, `repaired`에 `usedPart: true`와 `parts`(남은 수)를 싣는다. 메시지 형식은 필드 추가만 한다.
   - 서버는 홀드 시간을 검증하지 않는다(지금도 그렇다). 빠른 홀드는 클라이언트 표시다.
5. **스냅샷**: `snapshot`에 `parts`, `lastPartSlot`을 더한다. 프로토콜 1 소켓(레거시 스냅샷)에는 보내지 않는다.
6. **방어**: `collect`도 기존 소켓별 속도 제한(`rateLimit.ts`)을 탄다. 크기 제한도 같다.
7. **알람은 바꾸지 않는다.** 조각은 시간에서 나오므로 서버가 만들 일이 없다.

### B. 클라이언트

1. **조각 그리기**: 고장이 0개이고 `parts < PARTS_CAP`이며 지금 칸이 `lastPartSlot`보다 클 때, 지금 칸의 조각 하나를 `partPosition(slot)`에 그린다.
   - 생김새: 작은 금속 조각(낮은 다면체), 지면 위 살짝 떠서 천천히 돈다. 팔레트에 새 의미 색 하나를 더한다(선택 시안·고장 빨강·상태 초록·패널 호박·드론 흰빛과 구분). 바닥 돌조각과 헷갈리지 않게 금속광·회전을 준다.
   - 칸이 바뀌면 이전 조각은 사라지고 새 조각이 떨어진다(짧은 낙하).
2. **줍기**: 조각을 탭하면 `collect { slot }`을 보내고, 바로 작은 반응을 낸다(조각이 창고 쪽으로 빨려 들어가는 짧은 연출). 서버 확인(`parts.mine`)이 오면 HUD 수가 올라간다. 남이 주우면 조각이 그 자리에서 사라지고 HUD 수가 같이 오른다.
   - 탭 판정은 #105에서 고친 방식을 따른다. 조각은 탭 상자를 조금 크게 잡는다(폰 손가락).
3. **HUD**: 아랫줄 `함께 고친 7회 · ◆ 3명 접속 중`에 `부품 3`을 더한다. 0이면 `부품 0`도 보인다(모을 수 있다는 걸 알게).
4. **수리 패널**: 창고가 1 이상이면 수리 버튼을 `꾹 눌러 수리 (0.5초 · 부품 1)`로, 0이면 지금처럼 `꾹 눌러 수리 (1초)`로 보여준다. 홀드 길이는 누르기 시작할 때의 창고 수로 정한다. 누르는 도중 남이 부품을 써도 길이는 바뀌지 않는다.
5. **수리 결과**: `repaired.usedPart`가 true이고 내 수리면 토스트에 `부품 1개 사용`을 붙인다.

### C. 순수 로직과 테스트(TDD)

- 서버(`worker/state.ts`):
  - `collect`의 조건 분기(지금 칸·전 칸·미래 칸·같은 칸 두 번·상한·고장 중)
  - 수리 시 차감(0이면 차감 없음, 동시 수리 두 번에 부품 1개면 1개만 차감)
  - 저장본에 필드가 없을 때 기본값
  - 스냅샷·`repaired` 필드
- 공용(`shared/`): `partSlot(now)`, `partPosition(slot)`(결정성, 기지 반경 안, 모듈·탭 상자와 겹치지 않음, 연속 칸끼리 너무 가깝지 않음)
- 클라이언트: 조각을 보일지(고장 0·상한·칸 비교), 홀드 길이 결정(누르기 시작 때 고정), HUD 문구
- 프로토콜 파서: `collect`·`parts` 파싱, 모르는 필드 무시

## 하지 않는 것

- 개인 인벤토리, 계정, 부품 종류 여러 개, 부품으로 사는 업그레이드
- 창고가 비었을 때 수리를 막는 것
- 서버의 홀드 시간 검증
- 조각을 서버가 만들어 저장하는 것(시간에서 결정적으로 나온다)
- 정전 중 특별 규칙(정전 중에는 고장이 있으므로 조각이 안 떨어진다)

## Verification

- 서버 테스트(`npm run test:worker`): 위 C의 서버 항목, 같은 칸 두 번 `collect`에 +1만, 상한, 고장 중 무시, 마이그레이션 기본값, 레거시 소켓에 새 필드 없음
- 단위 테스트: 칸·위치 결정성과 겹침, 조각 표시 조건, 홀드 길이 고정, HUD 문구
- 클라이언트 2개: 한쪽이 주우면 다른 쪽에서 조각이 사라지고 `부품 N`이 같이 오른다. 같은 조각을 동시에 탭하면 +1만 된다. 부품 1개일 때 두 사람이 동시에 빠르게 고쳐도 둘 다 수리되고 창고는 0이 된다
- 창고 0에서 첫 방문자가 지금처럼 1초 홀드로 고칠 수 있다
- 페르소나 플레이테스트(009-2): 고장 없는 시간에 조각을 발견하고 줍는지, 부품으로 빨리 고친 것을 알아채는지. #101 지적(할 일 없음)이 줄었는지
- 번들: 초기 JS 450KB 이하. 성능: 드로우콜 +2 이하
- 사용자가 Preview를 폰·PC로 직접 확인
