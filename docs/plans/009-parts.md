# 009 — 공용 부품 창고: 부품을 주워 모으고, 그 부품으로 고친다

- 브랜치: `feat/009-parts`
- 등급: large
- 관련 이슈: Closes #101
- 마일스톤: M5 출시
- 상태: 플랜 리뷰

## Context

플레이테스트 세 번(PR #100, #104, #108)에서 페르소나 전원이 같은 말을 했다. 고장이 없는 시간(첫 접속 직후, 수리 직후)에 할 일이 없다. 재방문 의사는 "아니오" 또는 "모르겠다"였다(#101).

사용자 결정(#101, 2026-11-28): **공용 창고, 수리에 부품이 필요하다. 대신 부품은 언제든 구할 수 있다.**

- 기지 주변에 부품 조각이 계속 떨어진다(고장·정전 중에도). 누구든 탭하면 기지 공용 창고에 +1이 쌓인다.
- 수리 한 번에 창고 부품 1개가 든다. 창고가 0이면 수리할 수 없다.
- 첫 방문 보장(경험 원칙 3)은 "조각이 늘 화면에 있고 몇 초 안에 주울 수 있다"로 지킨다. 새 기지·빈 창고로 들어와도 첫 조각을 주우면 바로 고칠 수 있다.

이 기능은 `AGENTS.md`의 범위 줄("상호작용은 '수리' 1종")을 넓힌다. 범위 확장은 사용자 결정이다. 범위 줄은 별도 하네스 PR로 고친다.

새 상태는 **창고 수** 하나다(서버, 공용). 조각의 위치와 등장 시각은 시간에서 결정적으로 나오므로 상태가 아니다. 한 마일스톤에 상태 종류 2개까지라는 규칙 안이다. M5에서 이미 늘린 상태는 클라이언트 콤보 하나다.

경험 원칙:

- 1(다른 사람이 있다는 게 보인다): 남이 모은 부품으로 내가 빨리 고친다. 창고 수가 모두에게 같이 움직인다.
- 2(기지는 계속 살아 있다): 조각이 계속 떨어진다.
- 4(손맛): 줍는 탭에 작은 반응. 주운 부품이 수리로 이어지는 짧은 고리(줍기 → 고치기).

## 만들 것

### A. 서버 (DO)

1. **상태**: `BaseState`에 두 필드를 더한다.
   - `parts: number`: 창고 수, 0 이상 `PARTS_CAP`(5) 이하
   - `lastPartSlot: number`: 마지막으로 주운 조각의 칸 번호, 처음엔 -1
   - 저장 키는 `base:v2` 그대로다. 필드가 없는 저장본을 읽으면 `parts = 0`, `lastPartSlot = -1`로 채운다. 마이그레이션은 쓰기 없이 읽을 때 채우는 것뿐이다. **DO 저장 형식 변경이므로 이 플랜의 승인이 곧 그 승인이다**(`AGENTS.md` 멈춤 조건).
   - 롤백: 009 이전 서버로 `wrangler rollback`하면 옛 코드는 모르는 필드를 저장할 때 버린다. 창고 수가 0으로 돌아갈 뿐 기지 상태는 깨지지 않는다. 009-1 QA에서 옛 `loadState`가 새 필드가 붙은 저장본을 읽고 쓰는 테스트로 확인한다.
2. **조각 칸**: `slot = floor(serverNow / PART_SLOT_MS)`(`PART_SLOT_MS` = 10초). 재고장 간격 20~40초 동안 조각이 2~4개 떨어지므로 혼자서도 고장 하나당 부품 하나를 주울 수 있다. 10초는 폰에서 패널을 보고 조각을 찾아 탭할 시간이다. 칸 하나에 조각 하나다.
   - 위치는 `partPosition(slot)`이 정한다. 시드 해시로 정하고, 모듈·탭 상자와 겹치지 않는다. 위치는 **전체 시점 화면 안**(모듈 배치 범위 `BOUNDS` 안의 빈 땅)으로 제한한다. 위치 함수는 `shared/`에 두고 서버와 클라이언트가 같이 쓴다.
   - **시각 기준은 서버다**: 클라이언트는 스냅샷의 `serverNow`로 오프셋을 잡아(`src/net/` 기존 처리) 서버 시각으로 칸을 계산한다. 기기 시계가 틀려도 같은 칸을 본다.
3. **줍기 메시지**: 클라이언트 → 서버 `collect { slot }`.
   - 받아들이는 조건: `slot`이 지금 칸이거나 바로 전 칸이다(경계 여유). `slot > lastPartSlot`이고, `parts < PARTS_CAP`이다. 고장·정전 중에도 받는다.
   - 받아들이면 `parts += 1`, `lastPartSlot = slot`, `version += 1`을 하고 저장한 뒤 모두에게 `parts { count, slot, mine }`을 보낸다. `mine`은 요청한 소켓에만 true다.
   - 조건이 안 맞으면 무시한다. 같은 칸을 두 번 주울 수 없다(멱등).
4. **수리에 부품이 든다**: `repair { faultId }`는 `parts >= 1`일 때만 받아들인다. 받아들이면 `parts -= 1`을 하고 `repaired`에 `parts`(남은 수)를 싣는다.
   - `parts = 0`이면 수리를 무시하고 요청한 소켓에만 `repairRejected { faultId, reason: 'noParts' }`를 보낸다. 상태는 바뀌지 않는다(멱등).
   - 마지막 1개로 두 사람이 동시에 고치면 먼저 처리된 한 명만 수리되고, 다른 한 명은 `noParts`를 받는다. 같은 고장이면 두 번째는 원래대로 이미 고쳐진 고장이라 무시된다.
   - 서버는 홀드 시간을 검증하지 않는다(지금도 그렇다).
5. **스냅샷**: `snapshot`에 `parts`, `lastPartSlot`을 더한다. 프로토콜 1 소켓에는 새 필드와 새 메시지(`parts`, `repairRejected`)를 하나도 보내지 않는다.
6. **방어**: `collect`도 기존 소켓별 속도 제한(`rateLimit.ts`)을 탄다. 크기 제한도 같다.
7. **알람은 바꾸지 않는다.** 조각은 시간에서 나오므로 서버가 만들 일이 없다.
8. **새 기지**: 처음 만드는 기지는 `parts = 0`이다. 첫 고장은 5초 뒤(`FIRST_FAULT_WAIT_MS`)이고, 그 사이 조각 하나가 떨어진다.

9. **필요 여부 옵션**: 부품이 필요한지는 상태 함수의 인자(`opts.partsRequired`)로 주입한다. `BaseRoom`은 **코드 상수** `PARTS_REQUIRED`를 넘긴다(환경 값이 아니다). 009-2에서 이 상수와 `PROTOCOL_VERSION = 3`을 같은 커밋에서 바꾸므로 배포·롤백이 늘 함께 움직인다. 테스트는 인자로 두 값을 모두 돈다.
   - `false`: 줍기는 되고 창고도 쌓이지만, 수리는 차감·거절 없이 지금처럼 된다.
   - `true`: A.4대로 동작한다.
10. **옛 탭의 업그레이드 경로**: 009-2에서 `PARTS_REQUIRED`를 켤 때 `PROTOCOL_VERSION`을 3으로 올린다. `?protocol=2`로 붙은 옛 탭에는 `protocol: 3` 스냅샷을 보낸다. 옛 클라이언트는 지금 있는 장치(`src/net/socket.ts`: 모르는 프로토콜이면 수리 잠금 + 새로고침 배너)로 새로고침 안내를 받는다. 옛 탭이 조용히 실패하는 수리 버튼을 보는 일은 없다. 009-2 QA에서 옛 빌드(프로토콜 2) 대 새 서버 세션으로 확인한다.
    - 반대 방향(009-2 배포 뒤 롤백)도 같다. 프로토콜 3 탭이 롤백된 서버의 `protocol: 2` 스냅샷을 받으면 같은 장치로 수리 잠금 + 새로고침 배너가 뜨고, 새로고침하면 롤백된 클라이언트를 받는다.
11. **009-1과 이미 열린 탭**: 009-1은 프로토콜 2를 유지하고 `snapshot`·`repaired`에 필드만 더한다. 지금 main의 파서는 모르는 필드를 버린다(`shared/protocol.ts` 파서 주석). 009-1에 고정 입력 테스트를 둔다. **009-1 이전 커밋의 파서**로 새 필드가 붙은 메시지를 파싱해 기존 필드가 그대로 나오는지 확인한다. `parts` 메시지는 옛 파서가 모르는 `type`이라 무시되는지도 같이 본다.

### B. 클라이언트

1. **조각 그리기**: `parts < PARTS_CAP`이고 지금 칸(서버 시각 기준)이 `lastPartSlot`보다 클 때, 지금 칸의 조각 하나를 `partPosition(slot)`에 그린다(고장·정전과 관계없이). 정전 중에도 잘 보이게 조각은 스스로 빛난다. 칸이 끝나기 2초 전부터 깜빡여 곧 사라진다는 걸 알린다.
   - 생김새: 작은 금속 조각(낮은 다면체), 지면 위 살짝 떠서 천천히 돈다. 팔레트에 새 의미 색 하나를 더한다(선택 시안·고장 빨강·상태 초록·패널 호박·드론 흰빛과 구분). 바닥 돌조각과 헷갈리지 않게 금속광·회전을 준다.
   - 칸이 바뀌면 이전 조각은 사라지고 새 조각이 떨어진다(짧은 낙하).
2. **줍기**: 조각을 탭하면 `collect { slot }`을 보내고, 바로 작은 반응을 낸다(조각이 창고 쪽으로 빨려 들어가는 짧은 연출). 서버 확인(`parts.mine`)이 오면 HUD 수가 올라간다. 남이 주우면 조각이 그 자리에서 사라지고 HUD 수가 같이 오른다.
   - 탭 판정은 #105에서 고친 방식을 따른다. 조각은 탭 상자를 조금 크게 잡는다(폰 손가락).
   - 1.5초 안에 그 칸의 `parts` 확인이 오지 않으면(경계 초과·속도 제한으로 무시된 경우) 조각을 다시 보이게 하고 입력을 푼다. 그 사이 칸이 바뀌었으면 새 칸 조각을 보인다.
3. **HUD**: 아랫줄 `함께 고친 7회 · ◆ 3명 접속 중`에 `부품 3/5`를 더한다. 0이면 `부품 0/5`도 보인다(모을 수 있다는 걸 알게). 상한이면 조각이 안 떨어지는 이유가 보인다.
4. **수리 패널**: 창고가 1 이상이면 `꾹 눌러 수리 (1초 · 부품 1)`. 0이면 버튼 문구가 `부품을 먼저 주워요`가 된다. 이 버튼을 누르면 선택을 풀고 전체 시점으로 돌아가며 조각에 링 핑을 낸다. 조각은 전체 시점 화면 안에만 떨어지므로(A.2) 거기서 보인다. 누르는 도중 창고가 0이 되면 홀드를 멈춘다.
   - **이번 칸 조각이 이미 주워졌으면**(조각이 화면에 없으면) 버튼 문구는 `다음 조각 7초`처럼 남은 시간이다(서버 시각 기준, 초 단위). 누르면 전체 시점으로 돌아가고, 다음 조각이 떨어지는 순간 그 조각에 링 핑을 낸다.
5. **부품이 없을 때 안내는 하나로 통일한다**: 홀드 중 창고가 0이 됐을 때와 `repairRejected { reason: 'noParts' }`를 받았을 때(홀드가 끝나 수리 요청을 보낸 뒤의 응답 대기 해제) 모두 `부품이 없어요 — 조각을 주워요`를 보여준다.
6. **수리 결과**: 내 수리면 토스트에 `부품 1개 사용`을 붙인다.

### C. 순수 로직과 테스트(TDD)

- 서버(`worker/state.ts`):
  - `collect`의 조건 분기(지금 칸·전 칸·미래 칸·같은 칸 두 번·상한, 고장·정전 중에도 받음)
  - `partsRequired: true`: 수리 시 차감, 0이면 거절(상태 불변), 부품 1개에 서로 다른 고장 두 수리가 오면 하나만 성공
  - `partsRequired: false`: 차감·거절 없이 수리, 줍기는 됨
  - 저장본에 필드가 없을 때 기본값
  - 스냅샷·`repaired` 필드
- 공용(`shared/`): `partSlot(now)`, `partPosition(slot)`(결정성, 기지 반경 안, 모듈·탭 상자와 겹치지 않음, 연속 칸끼리 너무 가깝지 않음)
- 클라이언트: 서버 시각 기준 칸 계산(시계 오차), 조각이 없을 때 버튼 문구와 남은 초, 조각을 보일지(상한·칸 비교), 줍기 낙관 표시와 1.5초 복구, 수리 버튼 문구(창고 0), 홀드 중 창고 0이 되면 멈춤, `repairRejected` 처리, HUD 문구
- 프로토콜 파서: `collect`·`parts`·`repairRejected` 파싱, 모르는 필드 무시, 프로토콜 3 스냅샷을 프로토콜 2 파서가 비호환으로 판정(그 반대도), 009-1 이전 파서가 새 필드 붙은 메시지를 받아도 기존 필드가 그대로(A.11)

## Verification

- 서버 테스트(`npm run test:worker`): 위 C의 서버 항목, 같은 칸 두 번 `collect`에 +1만, 상한, 고장·정전 중에도 줍기, 마이그레이션 기본값, 레거시 소켓에 새 필드·메시지 없음, 옛 `loadState`가 새 필드 붙은 저장본을 읽고 씀(롤백)
- 단위 테스트: 칸·위치 결정성과 겹침, 위치가 전체 시점 화면 안, 서버 시각 기준 칸, 조각 표시 조건, 줍기 복구, HUD 문구
- 클라이언트 2개: 한쪽이 주우면 다른 쪽에서 조각이 사라지고 `부품 N`이 같이 오른다. 같은 조각을 동시에 탭하면 +1만 된다. 부품 1개일 때 두 사람이 서로 다른 고장을 동시에 고치면 한 명만 수리되고 다른 한 명은 거절 안내를 본다
- 새 기지·빈 창고로 들어온 첫 방문자가 조각을 주워 첫 고장을 고칠 수 있다(설명 없이). 정전 중에도 조각을 주워 발전기를 고칠 수 있다
- `PARTS_REQUIRED = false`(009-1만 배포)에서는 지금처럼 부품 없이 수리된다
- 옛 탭(프로토콜 2)이 열린 채 009-2가 배포되면 수리 잠금과 새로고침 배너가 뜬다. 009-2 뒤 롤백하면 프로토콜 3 탭에도 같은 배너가 뜬다
- 창고 0이고 이번 칸 조각이 이미 주워졌으면 버튼이 남은 초를 보이고, 다음 조각이 떨어질 때 링 핑이 난다
- 기기 시계를 1분 틀리게 한 브라우저에서도 조각을 주울 수 있다
- 페르소나 플레이테스트(009-2): 처음 온 사람이 "부품을 먼저 주워요"에서 막히지 않고 조각을 찾아 줍는지, 고장 없는 시간에 조각을 모으는지. #101 지적(할 일 없음)이 줄었는지
- 번들: 초기 JS 450KB 이하. 성능: 드로우콜 +2 이하
