- 브랜치: `feat/008-launch`
- 등급: large
- 관련 이슈: Refs #91, Refs #82, Refs #85
- 마일스톤: M5 출시

## Context

M2~M4에서 기지·공유 상태·성능을 만들었다. 남은 문제는 셋이다.

1. **고른 게 모양으로 안 보인다**(#91). 모듈을 누르면 카메라가 붙고 이름표가 뜨지만 모듈 자체는 그대로다. 무엇을 고르고 있는지는 카메라 움직임으로만 알 수 있다.
2. **화면이 한 톤이 아니다**(#82). 폰 첫 화면은 아래 35~40%가 빈 바닥이다. 태양광 패널 밭의 남색과 밝은 테두리가 모듈과 시선을 다툰다.
3. **이펙트 6~8이 아직 없다**(`docs/content-plan.md` 피드백 이펙트). 수리 1~5는 있다.

이 PR은 새 서버 상태를 만들지 않는다. 클라이언트 상태는 하나(콤보 카운트, C.2)만 늘린다. 선택 링·아웃라인은 이미 있는 선택 상태를 보여줄 뿐이다. 손맛과 보이는 품질만 다룬다(`AGENTS.md` "읽을 상태를 늘리기 전에 손맛 먼저").

경험 원칙: 3(들어오자마자 알 수 있다 — 첫 화면에 기지가 꽉 차고, 고른 것이 보인다), 4(손맛은 진하게), 5(폰이 기준 화면이다 — 폰도 PC와 같은 화면을 본다).

**비주얼 방향(사용자 결정, #99 비교)**: 후처리를 포함한 최대 비주얼이 **모든 기기의 기본**이다. 기기 종류(터치 여부)로 효과를 미리 빼지 않는다. 느린 기기는 품질 사다리가 단계적으로 덜어낸다(B.6). 비교용 PR #99(`?look=max`/`?look=budget`)에서 최신 폰이 max로 60fps를 냈다.

## 만들 것

### A. 아트 방향 (#82)

1. **팔레트를 한 곳에 둔다**: `src/scene/palette.ts`에 의미별 색을 모은다. 고장(빨강), 수리 완료·상태등(초록), 선택(새 색), 비상등, 패널 켜짐·꺼짐, 안개(평상시·정전)가 들어간다. 지금 흩어져 있는 색 상수(`fx/StatusLight`, `fx/shared`, `panels.ts` 등)는 여기를 참조한다.
   - 선택 색은 빨강·초록과 겹치지 않는 색이다(시안 계열 후보). 고장 모듈을 선택해도 빨간 펄스와 선택 표시가 구분돼야 한다(#91 걸리는 것 3).
   - 테스트: 선택 색과 고장·수리·비상등·패널 켜짐 색의 색상(hue) 거리가 최소값 이상이다. 선택 색과 바닥·안개 색의 명도 대비가 최소값 이상이다.
2. **폰 첫 화면 프레이밍**: 세로 화면(가로/세로 비 1 미만)에서만 바꾼다. 비 1 근처(태블릿 분할 화면·창 크기 조절)에서 계단처럼 튀지 않게, 비 0.8~1.0 구간은 세로용 값과 가로용 값을 보간한다. 모듈 5개가 화면 세로 가운데 영역을 채우고, 아래 빈 바닥은 화면의 20% 이하로 줄인다.
   - `framing.ts`의 폭 맞춤 계산과 세로 화면용 여백·극각을 다시 잡는다. 가로 화면 값은 그대로 둔다.
   - 테스트(기존 `framing` 테스트 확장), 390x844·360x780·320x568 기준:
     - 모듈 점들의 화면 투영에서 가장 아래 점과 화면 아래 사이 여백이 20% 이하다.
     - 가장 아래 점(고장 바닥 링의 바깥 끝 `floorRingRange(id).to` 포함)이 하단 UI 영역(HUD 하단 줄 높이 + 안전 영역 여유) 위에 있다.
     - 이름표·배지 자리가 화면 위 HUD에 가리지 않는다.
     - 320 폭에서 좌우 여백이 각각 화면 폭의 4% 이상이다.
   - PC 회귀: 1280x800·1920x1080·2560x1080에서 투영 결과가 지금과 같다(허용 오차 안).
   - 선택 시 시점은 바꾸지 않는다(패널과 겹침은 M4에서 맞춘 `FOCUS_OFFSET`이 맡는다).
   - 소행성대 시선 조건(`asteroids.test.ts`)은 그대로 통과해야 한다.
3. **거리 안개**: `scene.fog`를 선형 안개로 넣는다. 색은 하늘 그라디언트(B.2에서 씬 배경으로 옮긴다) 아래쪽 색과 같은 값이다. 패널 밭·바깥 바위가 뒤로 물러나 보이게 한다. 모든 기기에 켠다.
   - `THREE.Fog`는 카메라 거리 기준이므로 `near`/`far`를 **카메라와 시선 대상(target) 사이 거리에 연동**한다. 예: `near = d + 여유`, `far = d + 범위`. 그러면 폰 첫 화면(먼 카메라)이든 모듈 포커스(가까운 카메라)든 모듈은 늘 안개 밖에 있다. 매 프레임 숫자만 바꾸고 할당하지 않는다.
   - 테스트: 폰·PC 첫 화면과 각 모듈 포커스 시점에서 모듈 점들의 카메라 거리가 `near`보다 작고, 지면 페이드 반경(`GROUND_FADE_RADIUS`) 지점은 `far` 근처다.
   - 안개를 받지 않는 것(`fog: false`): `toneMapped: false` 재질 5곳(글로우·스파크·상태등·패널 램프·`fx/shared`), 별, 소행성대. 원경(별·소행성대)은 지금처럼 보인다.
   - 정전: 안개 색과 하늘 배경을 **같은 진행값**(정전 전환 길이·곡선을 담은 상수 하나, `Lighting`의 정전 보간과 공유)으로 어두운 색으로 보간한다.
4. **패널 밭 톤**: 패널 본체의 채도·명도를 낮추고 테두리 대비를 줄인다. 모듈이 시선의 주인이 되게 한다. 정전 소등·순차 점등(#54)은 그대로다.
5. **선택 시 고장 문구 중복 제거**: 고장 모듈을 선택하면 패널이 고장 문구와 센서 줄을 보여주므로, 그 모듈 위의 3D 고장 배지는 숨기고 이름표만 남긴다. 선택하지 않은 고장 모듈의 배지는 지금처럼 보인다(첫 화면에서 고장이 보여야 한다, 경험 원칙 3). `labelRules`에 규칙과 테스트를 더한다.
6. #82의 나머지 제안은 이 PR에서 하지 않는다(`하지 않는 것`).

### B. 선택 표시와 후처리 (#91)

1. **선택 표시는 후처리와 무관하게 그린다**: 모든 기기, 모든 품질 단계에서 같다.
   - **선택 링**: 선택한 모듈 바닥에 선택 색의 얇은 링. 고장 표시용 바닥 링(`FloorRing`, 빨간색, 바깥으로 맥동)과 별도 메시다. 선택 링은 맥동하지 않고 탭 상자 바로 바깥 반경에 고정한다. 고장 링은 그 바깥 `floorRingRange`에서 맥동한다. 고장 모듈을 골라도 색(시안/빨강)과 움직임(고정/맥동)으로 둘이 구분된다.
   - **아웃라인**: 선택한 모듈 **본체 메시**(GLB 모델의 메시만, 상태등·글로우·스파크·링 같은 fx 자식 제외)를 중심 기준으로 살짝 키운 뒷면(`BackSide`) 단색 메시(inverted hull). 메시 중심 기준 확대라 모서리가 튀지 않는다(#99에서 확인). 지오메트리는 모델 것을 공유하고, 재질은 하나를 재사용한다.
   - 후처리 `Outline` 패스는 쓰지 않는다. #99에서 선택 객체를 잡고도 화면에 아무것도 그리지 못했고, 깊이·마스크 패스를 더 돈다.
2. **하늘을 씬 배경으로 옮긴다**: 지금 캔버스 뒤 CSS 그라디언트(`SKY_GRADIENT`, `SKY_GRADIENT_DARK`)를 같은 색의 그라디언트 텍스처 `scene.background`로 옮긴다. 컴포저가 투명 캔버스를 보장하지 않기 때문이다(#99). 정전 때는 배경을 어두운 그라디언트로 보간한다(A.3의 안개와 같은 진행값). 하늘·안개·지면이 모두 같은 렌더·톤 매핑을 지나므로 지평선 이음새가 생기지 않는다.
3. **후처리 스택(모든 기기)**: `@react-three/postprocessing`의 `EffectComposer`. 패스 순서는 다음과 같다.
   - 렌더 → N8AO(SSAO) → Bloom(이미시브·글로우만 빛나게 휘도 임계값으로 고름) → `ChromaticAberration`(평소 0, C.3) → Vignette → 약한 Noise → `ToneMapping`(ACES) → SMAA
   - 렌더러 톤 매핑은 끄고(`NoToneMapping`) 톤 매핑은 `ToneMapping` 효과가 한 번만 맡는다.
   - 값은 #99의 `look=max`에서 출발한다(Bloom 임계값 1.2, Noise 불투명도 0.08).
4. **기존 이펙트 밝기**: `toneMapped: false` 재질 5곳(`fx/Glow`, `fx/StatusLight`, `fx/Sparks`, `fx/shared`, `SolarPanels` 램프)은 컴포저 톤 매핑을 함께 지나므로 **컴포저 경로 기준으로** 다시 맞춘다. 후처리가 꺼진 경로(B.6 마지막 단계, B.5 실패)는 저하 모드라 밝기 차이를 허용한다. 맞춘 값과 두 경로 스냅샷을 PR 본문에 남긴다.
5. **로딩과 실패**: 후처리 코드는 `src/scene/post/` 한 곳에서만 import하고 동적 import로 별도 청크로 불러온다. 씬 컴포넌트는 후처리 라이브러리를 import하지 않는다. 초기 JS 예산 450KB를 지키기 위해서다.
   - 청크는 첫 화면 GLB·스냅샷과 **동시에** 불러온다. 로딩 배너는 씬 준비와 후처리 준비를 둘 다 기다린다. 다만 씬 준비 뒤 후처리를 기다리는 시간은 최대 2초다.
   - 2초가 지나거나, 불러오기·컴포저 초기화(렌더 타깃 포함)가 실패하면 그 세션은 후처리 없이(`plain`) 간다. 렌더러 톤 매핑을 켜고, 나중에 도착한 청크는 쓰지 않는다. 실패는 후처리 전용 ErrorBoundary가 잡는다.
   - 테스트(UI 로직): 로드 결과·시간 초과 → `postMode`(`composer` | `plain`)와 렌더러 톤 매핑 값.
6. **품질 사다리 확장**: 지금 단계(0~4: dpr·소행성 절반·바깥 바위)를 내려간 뒤에도 느리면 후처리를 덜어내는 단계를 더한다.
   - 5: N8AO 끔 → 6: Bloom 끔 → 7: 컴포저 전체 끔(`plain`, 렌더러 톤 매핑 켬)
   - 이 세 단계는 셰이더 재컴파일이나 패스 재구성으로 **한 번 멈칫**할 수 있다. 그래서 **내려가기만 하고 다시 올라가지 않는다**(세션 안에서 단방향). 007 C.9의 "런타임에는 재컴파일 없는 것만" 전제는 0~4단계에만 적용하고, 5~7단계는 이 예외로 적는다.
   - 기존 상승·바닥 규칙(`DROP_GAIN`, 프레임 상한 기기의 되돌리기)은 0~4단계에만 적용한다. 5~7단계는 효과가 없어도 되돌리지 않는다.
   - 테스트: 단계 4에서 계속 느리면 5→6→7로 내려가고, 빨라져도 4 이하로 올라가지 않는다. 컴포저 없는 세션(`plain`)은 5~7단계를 건너뛴다.
7. **안티에일리어싱**: 컴포저를 쓰면 캔버스 MSAA가 꺼지므로 SMAA로 대신한다.

### C. 이펙트 6~8

1. **카메라 셰이크(6)**: 내가 수리를 끝낸 순간(`repaired.mine`)에만 짧게(0.25초 안팎) 흔든다. 남이 고친 수리, 함께 고친 수리(`helped`), 정전에는 흔들지 않는다.
   - 진폭·감쇠는 순수 함수 `shakeOffset(elapsed)`(테스트: 0에서 시작, 끝나면 0, 최대 진폭 이하).
   - **렌더를 가로채지 않는다**: CameraControls 갱신보다 **앞선** `useFrame` 우선순위(음수)에서 직전 프레임에 더한 오프셋을 빼고, CameraControls 갱신 **뒤**(우선순위 0, 렌더 전)에서 이번 오프셋을 더한다. 렌더는 R3F 기본 렌더나 컴포저가 그대로 맡는다. 셰이크 컴포넌트는 `gl.render`를 부르지 않고 양수 우선순위를 쓰지 않으므로 후처리 유무(`postMode`)와 무관하다. CameraControls는 늘 오프셋을 뺀 위치에서 갱신한다. 오프셋 벡터는 미리 만들어 두고 `useFrame` 안에서 할당하지 않는다.
   - 포커스 이동 오버슈트는 하지 않는다. CameraControls의 짧은 경로 보간(M4에서 고침)과 다투기 때문이다.
2. **콤보(7)**: 내가 연달아 고치면 `x2`, `x3`을 수리 완료 팝업(`+1 REPAIR`) 옆에 띄운다.
   - "내 수리"는 서버가 보내는 `repaired.mine`으로 판정한다(프로토콜 변경 없음).
   - 연속의 기준: 이전 내 수리 완료에서 **15초 안**에 다음 내 수리를 끝낸 경우. 비어 있던 기지에 들어오면 고장이 2개 있고(`UNATTENDED_FAULT_CAP`), 홀드 수리는 몇 초면 끝나므로 지금 리듬에서도 일어난다. 기준값은 상수로 둔다.
   - 남의 수리와 `helped`는 **완전히 무시**한다. 콤보 값도 시간 창도 바꾸지 않는다(내 수리 A → `helped` B → A에서 15초 안 내 수리 C면 `x2`).
   - 클라이언트 표시만이다. 서버·저장·HUD 누적 수리 수는 바뀌지 않는다. 재연결해도 콤보 값은 메모리에 남고, 시간 창 판정만 따른다.
   - 순수 함수 `nextCombo(prev, event)`(테스트: 첫 수리 1, 창 안 연속 증가, 창 밖 1로 리셋, 남의 수리·`helped` 무시).
3. **색수차(8)**: 정전이 **라이브로 시작되는 순간**(받은 메시지로 정상 → 정전 전이를 본 경우)에만 0.4초 동안 `ChromaticAberration`을 세게 냈다가 0으로 줄인다.
   - 이미 정전인 기지에 접속하거나 재연결해서 받은 스냅샷으로는 발동하지 않는다.
   - 효과는 컴포저에 늘 붙어 있고 평소 오프셋은 0이다(붙였다 떼면 재컴파일). 컴포저가 없으면(`plain`) 발동하지 않는다.
   - 노이즈는 B.3에 상시로 있다. 효과음은 넣지 않는다.
4. **`prefers-reduced-motion`**: 셰이크와 색수차 펄스를 끈다. 이 조건은 각 효과를 넣는 PR(C.1은 008-3, C.3은 008-2)이 자기 효과에 함께 넣는다. 선택 링은 원래 움직이지 않는다. 기존 수리 연출(펀치·스파크)은 이 PR에서 바꾸지 않는다.

### D. 혼자 들어온 사람의 리듬 측정 (#85)
