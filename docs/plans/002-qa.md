## 반려 사유와 재현 방법

공통 준비: `hosts.yml`에 `user: chillingdaisy-worker1`가 있는 가짜 gh 폴더를 만든다. `gh pr view 2`는 `size:large`, 그 외는 `size:small`을 돌려주는 가짜 `gh`를 PATH 앞에 둔다(`guard-bash.test.sh`와 같은 방식).

```sh
probe() { # probe <agent|bare> <command>
  input=$(jq -n --arg c "$2" --arg d "$PWD" '{tool_input:{command:$c},cwd:$d}')
  if [ "$1" = agent ]; then
    env GH_CONFIG_DIR=$FAKE/gh-agent GIT_CONFIG_COUNT=2 \
      GIT_CONFIG_KEY_0=credential.https://github.com.helper GIT_CONFIG_VALUE_0= \
      GIT_CONFIG_KEY_1=credential.https://github.com.helper 'GIT_CONFIG_VALUE_1=!gh auth git-credential' \
      PATH=$FAKE/bin:$PATH scripts/hooks/guard-bash.sh <<<"$input"
  else
    env -u GH_CONFIG_DIR -u GIT_CONFIG_COUNT PATH=$FAKE/bin:$PATH scripts/hooks/guard-bash.sh <<<"$input"
  fi; echo "exit=$?"
}
```

1. 머지 제한 — 기대는 exit 2, 실제는 exit 0
   - `probe agent 'gh pr merge 1 --auto && gh pr merge 2 --auto'` (PR 2 = large)
   - 비교: `gh pr merge 1 --squash && gh pr merge 2 --auto`는 첫 구간이 걸려서 막힌다. 반대 순서인 `gh pr merge 1 --auto && gh pr merge 2 --squash`는 통과한다
   - 서버 쪽 방어(Approve 필수, large + 예약이면 pr-check 실패)가 있어서 바로 사고로 이어지지는 않는다. 그래도 플랜이 정한 훅 동작과 다르다
   - 수정: `merge_seg`를 `head -1`로 하나만 고르지 말고 모든 `gh pr merge` 구간을 돌며 검사한다
2. fail-closed 미탐 — 모두 `bare`에서 기대는 exit 2, 실제는 exit 0
   - `probe bare 'gh api --method=DELETE repos/o/r/issues/comments/1'`
   - `probe bare 'gh api -fbody=hi repos/o/r/issues/1/comments'`
   - `probe bare 'git -c core.x=y push origin feat/x'`
   - `probe bare 'git --no-pager push origin feat/x'`
   - `probe bare '(gh pr create --title x)'`
   - 수정 방향
     - `--method[[:space:]=]+`로 바꾼다
     - 짧은 플래그는 `[[:space:]]-[fF]([[:space:]=]|[^[:space:]-])`처럼 값이 붙은 형태도 잡는다
     - `git_opt`는 `git([[:space:]]+(-C[[:space:]]+\S+|-c[[:space:]]+\S+|--[a-z-]+(=\S+)?))*`로 넓힌다
     - `split_segments`에서 구간 앞의 `(`·`{`를 벗긴다
     - 각 케이스를 `guard-bash.test.sh`에 추가한다
3. (막지는 않음) 신원 변수 덮어쓰기 미탐 — `agent`에서 기대는 exit 2, 실제는 exit 0
   - `export A=1 GH_CONFIG_DIR=/tmp/x`: 첫 정규식은 `export` 바로 뒤의 변수만 본다
   - `declare -x GH_CONFIG_DIR=/tmp/x`
   - `FOO="a b" GH_TOKEN=x gh pr create --title x`: `guard-bash.sh:244`의 `[^[:space:]]*`가 따옴표 속 공백에서 끊긴다
   - `gh auth status --show-token`, `gh auth git-credential get`: 토큰을 꺼낸다. 플랜 목록에는 없지만 "토큰을 꺼내지 않는다"는 의도에 어긋난다

## 제안

1. `scripts/watch-pr.sh:4` 주석에 `<!-- agent -->` 표식 설명이 남아 있다. 지운다.
2. `agent_gh_ok`(`scripts/hooks/lib.sh:56`)는 프로세스 env의 `GH_TOKEN`·`GITHUB_TOKEN`을 보지 않는다. 이 값이 있으면 gh가 설정 폴더보다 토큰을 먼저 쓰므로 fail-closed가 통과한 채 다른 계정으로 나간다. SessionStart의 `gh api user` 점검은 경고만 낸다. 비어 있는지 함께 검사한다.
3. neon 차단 규칙(`guard-bash.sh:280`)에 오탐이 두 가지 있다. 하나는 `gh api -X GET … -f …` 형태의 읽기다. 다른 하나는 neon 리뷰를 언급만 한 코멘트("… 반영했습니다")다. 앞의 것은 `-X GET`이면 쓰기로 보지 않으면 된다. 뒤의 것은 본문이 고정 머리줄로 시작할 때만 막으면 watch-pr 분류와 기준이 같아진다.
4. 구간 분리가 따옴표를 무시해서 오탐이 난다. 커밋 메시지 `git commit -m "docs: note; GH_TOKEN=x is forbidden"`가 막힌다. 문서·커밋에서 이런 문장을 쓸 일이 있으니 알려진 한계로 테스트에 주석을 남긴다.
5. 사용자 label 승인 잡을 걷어냈으니 `pr-check.yml`에 `concurrency: { group: pr-check-${{ github.event.pull_request.number }}, cancel-in-progress: true }`를 둘 수 있다. 그러면 이벤트가 몰릴 때 늦게 끝난 옛 실행(예약 전 상태를 읽은 run)이 최신 결과를 덮는 경합이 없어진다.
6. `agent-env.sh`의 `git credential fill`에 `GIT_TERMINAL_PROMPT=0`을 준다. env가 없는 세션에서는 osxkeychain(Xcode 시스템 gitconfig)이 응답하거나 터미널 입력을 기다릴 수 있다.
7. 플랜 밖이지만 `gh api -X PUT repos/…/pulls/N/merge`와 GraphQL `mergePullRequest`·`enablePullRequestAutoMerge`는 머지 제한을 거치지 않는다. 실수 방지 훅이라는 범위 안에서 PUT `…/merge`만이라도 막을지 정한다.
